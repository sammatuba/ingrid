The panel derives the frozen six-key view of two saved probe bundles: the composed label on
each side with the information cutoff read from that side's saved task, `changed` rendered as
question names (`Q3 time`), and `new_passages` resolved to the later task's own passage quote,
publisher and availability, with the reference shown when a passage is not in this projection.
Every value is written with `textContent`; no field is parsed as markup.

The request is the frozen `GET /v1/tenants/{t}/cases/{c}/probe-bundles/pair` with the two
references as percent-encoded JSON query values, built in the compare handler. A refusal is
shown as text — the typed code and its sentence from `PAIR_MESSAGES`, which
`PairViewContractTests` asserts is `src/review/pairing.PAIR_MESSAGES` itself — never as a
numeric status. The view is read-only and stored nowhere: the panel writes no record, and the
route's read-only property is CORE-4's own evidence.

**No pair when only one task exists.** The compare control is disabled unless the selected
assumption has two different saved bundles among its compiled reviews
(`pairOptions.length < 2 || $('pair-before').value === $('pair-after').value`), and the panel
then shows the reason instead of a view: *"Only one compiled review exists for this
assumption, so there is no pair to show."* With no probe backend the panel reports
`bundle_available !== true` and leaves manual review and the cited brief untouched.

## Fixture provenance (no invented case facts)

The three fixtures embedded in `app.js` were produced by running the repository's own code:

* the two tasks and two saved bundles are the CORE-4 view test's own `setUp`
  (`tests/test_pairing.PairViewTests`), imported rather than copied: one snapshot at two
  information cutoffs (`2026-10-05T02:00:00Z`, `2026-10-07T00:00:00Z`) with a second fictional
  source known between them, compiled through the real repository and saved through the real
  `SystemOneService` over the labelled `FixtureSystemOne` double;
* `moved.view` is the return of the real `src.review.pairing.pair` over those two bundles:
  labels `challenges → challenges`, `changed = [q3_time, q6_observation]`, one new passage
  (`passage:fictional-return`, `"Unit A returns from its fictional outage on 5 October."`);
* `refused.error` is `{'code': 'PAIR_CUTOFF_ORDER'}` from a real `pair()` call with the two
  bundles in the order the panel lets the analyst choose (the later one on the before side);
  the body shape `{'code': …}` is `src/api/__init__.py`'s `error(code, status)`, and the route
  answers it at 422, as CORE-4's integration test asserts;
* `single` is the first task and its bundle alone, so the panel has one task and no pair.

Each fixture carries a *projection* of the fields the panel reads — `tasks[].record`
(`record_kind`, `record_id`, `revision_id`, `content_digest`, and
`payload.{assumption_ref, snapshot_ref, information_cutoff, context}`) and
`probe_bundles[]` (`…, payload.{task_ref, composed.label}`) — with the values copied from the
records. Generator, verifier and the node harness live outside the repository tree under
ignored `.local/ui-2/` (`make_pair_fixtures.py`, `embed_pair_fixtures.py`,
`verify_pair_view.py`, `check_pair_preview.mjs`); the embedded literal is written by
`embed_pair_fixtures.py` from the generated bytes, never re-typed. The fixture document is
13,280 bytes and must stay free of backticks and `${`, which the generator asserts.
